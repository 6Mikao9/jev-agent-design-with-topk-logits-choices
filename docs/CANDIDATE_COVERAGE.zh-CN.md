# I2：候选覆盖诊断与恢复

作者：匿名作者 · 版本：v0.4-design · 日期：2026-09-23

本文单独讨论选择型 agent 的候选覆盖问题，与[主设计](DESIGN.zh-CN.md)的 Top-k 回退流程配套。内容为拟议机制和评估方法，尚无实验结果。

## 1. 为什么单独提出这个问题

Jev 每次面对的是给定候选。如果所有选项都不满足任务，它仍可能对其中一个给出集中的概率。系统需要知道何时应该继续找选项，而不是把当前集合中的最高概率项直接执行。

“Jev 对所有投机候选都不满意”在实现中可以表现为选择显式 `FALLBACK_TOPK` 或其他恢复动作。这个出口使拒绝草案成为可能，但不保证拒绝判断准确。

TypeSafe 的 confidence 来自候选概率分布，不是对候选集合完整性的独立证明。[Confidence 定义](https://docs.typesafe.ai/confidence)

## 2. 区分几种失败原因

| 情况 | 可观察的线索 | 可以考虑的恢复动作 |
| --- | --- | --- |
| 候选间存在歧义 | 多个候选满足已知条件，偏好依据不足 | 补充判别信息或澄清 |
| 候选违反明确约束 | schema、参数范围或前置条件校验失败 | 修复、重新提案或排除候选 |
| 必要事实缺失 | 实体、字段含义、环境状态尚未确认 | 查询环境或询问用户 |
| 候选可能未覆盖正确动作 | 候选同质、约束无法由现有草案同时满足、历史同类失败 | 扩展候选来源、重新提案或 Top-k 构造 |
| 状态已经变化 | 用户修正、工具版本或资源状态更新 | 交给 I3 使依赖失效并局部重规划 |

这些情况可能同时发生。诊断记录可以保留多个原因及其证据，不能仅按一个概率阈值强制归类。

## 3. 拟议诊断信号

第一层是可直接检查的约束、实体与版本信息。第二层是候选生成过程的统计信息，包括来源数量、重复比例、覆盖的参数分支和曾经失败的条件。第三层才是模型判断与选择稳定性。

可以在研究中尝试候选去重、顺序扰动和受控增删，并观察选择变化。这些只是诊断信号；所有扰动下都选择同一项，也不能证明正确选项已经出现。[Grade Score](https://arxiv.org/abs/2406.12043) 已讨论选项顺序和选择一致性，需要据此限定相关贡献。

每次决策记录为与当前状态、问题和候选集合共同关联的输出。候选集合改变后生成新的集合 ID，重新评估，不直接把新旧概率当作同一尺度比较。

## 4. 与 Top-k fallback 的关系

主流程优先尝试完整参数或片段草案，显式提供以下控制选项：

```text
FALLBACK_TOPK   现有草案不适用，转为逐步构造该字段
REPROPOSE      刷新完整字段或片段候选
LOOKUP         查询缺失的环境信息
CLARIFY        向用户澄清缺失要求
STOP_UNRESOLVED 结束并报告未解决部分
```

`FALLBACK_TOPK` 只有在存在支持 logits 的辅助模型及剩余预算时才可用。它保留 Jev 的选择权，由辅助模型提供候选 token。Top-k 路径也可能遗漏正确 token，需要扩大 k、重新提案或回到有效检查点等出口。

若问题是未知资源 ID 或用户尚未确定的要求，Top-k 不会凭空获得事实，应先观察或澄清。若问题是字段组合方式不合适、而事实已经齐全，则细粒度构造可能有价值，但需实测。

## 5. 评估设计

建立可控制候选集合的任务：刻意移除正确项，加入近义重复项、无关项或违反约束的项；另外构造必要事实缺失和状态变化案例。比较以下策略：

1. 只选择最高概率候选。
2. 仅使用 confidence 阈值。
3. 增加显式拒绝与 `FALLBACK_TOPK` 选项。
4. 加入约束、覆盖风险和信息缺口诊断，再选择恢复动作。

统计高置信错误执行率、候选覆盖率、错误触发回退的比例、应回退却未回退的比例、恢复后成功率，以及所有前序提案和回退调用的总成本。诊断要在独立任务上评估，不在同一批任务上同时调阈值和报告最终结果。

## 6. 当前边界

I2 是独立研究问题。主设计已经具有拒绝与恢复出口，尚未声称实现了可靠的候选缺失检测。正确候选本身的生成难度、模型对控制选项的理解，以及校准信号跨工具是否有效，都需要后续研究。
